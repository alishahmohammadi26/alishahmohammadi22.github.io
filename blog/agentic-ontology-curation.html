1. The Ontology Problem in Drug R&D

Walk through any pharmaceutical research organization and you will find the same terminology fragmentation problem everywhere. A process development scientist in San Diego writes "cell viability" in her ELN. Her counterpart in Osaka records the same measurement as "VIAB %". The LIMS in the clinical manufacturing facility in Switzerland stores it as "Viability_Score_Trypan". The regulatory submission uses the official ontology term OBI:0001985 from the Ontology for Biomedical Investigations — but only because a data steward manually looked it up six weeks before the BLA submission deadline.

These four strings represent the same scientific concept. No machine knows that. No AI/ML model trained across these four systems will generalize correctly. The downstream cost is not merely inconvenient — it directly blocks the kind of cross-dataset meta-analysis and federated AI that could accelerate drug development by years.

The scale of the problem A mid-size pharmaceutical company generates 3–5 million new data points per year across its R&D estate. Industry surveys suggest that 60–70% of these contain unmapped or inconsistently mapped terminology. At that scale, manual curation by domain stewards — typically 2–4 FTEs per therapeutic area — is not a viable long-term strategy.

Biomedical ontologies exist precisely to solve this. The Gene Ontology (GO), ChEBI, OBI, BAO, NCI Thesaurus, and dozens of other controlled vocabularies collectively cover the semantic space of pharmaceutical R&D. The challenge is not the absence of ontologies — it is the cost and latency of mapping real-world data to them at scale.

Traditional approaches use keyword matching or simple string similarity. These fail on abbreviations, synonyms, assay variants, and domain-specific jargon. A probabilistic match of "VIAB %" to OBI:0001985 requires understanding that "VIAB" is a context-specific abbreviation for "viability", that the "%" suffix is a unit annotation rather than part of the concept name, and that in the context of cell culture assays this specific OBI term is preferred over the more generic NCIT alternative.

This is exactly the kind of multi-step reasoning task that large language models, properly constrained and orchestrated, can now perform reliably.

2. Why an Agentic Architecture?

The naive approach is a single LLM call: "Here is a data field label and some context — which ontology term does it map to?" This works surprisingly well for straightforward cases. It fails, predictably, at scale and at the edges.

The failure modes are instructive:

  • Hallucinated ontology identifiers. LLMs confidently generate plausible-looking but non-existent CURIEs. Without a verification step against a live ontology API, these errors propagate silently into the knowledge graph.
  • Ambiguous mappings without confidence scoring. A single LLM call cannot surface the fact that "cell viability" maps plausibly to both OBI:0001985 and BAO:0002166 with different semantic precedence depending on assay context.
  • No cross-dataset conflict detection. If dataset A maps "VIAB" to one term and dataset B maps "Cell Viability" to a different term, a single-call architecture has no mechanism to detect the inconsistency or escalate for resolution.
  • No governance integration. Scientific terminology decisions in regulated environments require documented human approval. A single LLM call produces an answer but no audit trail, no routing, no approval workflow.

An agentic architecture addresses each failure mode with a dedicated, specialized component. Each agent has a narrow, well-defined responsibility, uses only the tools relevant to its task, and passes structured state to the next stage. The orchestration layer — in this case LangGraph — manages state transitions, conditional routing, and the human-in-the-loop interrupts.

Design principle The goal is not to replace domain stewards. It is to eliminate the 80% of curation work that is mechanical — term lookup, synonym matching, duplicate detection — so that stewards can focus on the 20% that requires scientific judgment.

3. System Architecture: Four Agents, One Pipeline

The OntoCurator system is built on four specialized agents orchestrated through a LangGraph state machine. Each agent is a self-contained LangChain Runnable with its own prompt template, tool bindings, output schema, and error handling.

4. Agent 1 — EntityExtractorAgent

The first agent is a GPT-powered named entity recognizer specialized for pharmaceutical R&D documents. Unlike general biomedical NER models (e.g., BioBERT fine-tuned on CRAFT or BioNLP corpora), this agent is designed to handle the messy, contextual language found in internal ELN entries, process descriptions, and analytical method summaries.

The agent extracts entities across five semantic types: Measurement (e.g., cell viability, process yield), BiologicalEntity (cell lines, organisms, targets), ChemicalEntity (buffers, excipients, APIs), ProcessParameter (temperature, pH, agitation rate), and Assay (ELISA, flow cytometry, HPLC).

entity_extractor.py 
from pydantic import BaseModel, Field
from typing import List, Literal
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

class EntitySpan(BaseModel):
    text: str = Field(description="Exact text of the entity as it appears in the source")
    normalized: str = Field(description="Lowercase normalized form without units or suffixes")
    entity_type: Literal["Measurement", "BiologicalEntity", "ChemicalEntity",
                                "ProcessParameter", "Assay"]
    confidence: float = Field(ge=0.0, le=1.0)
    context_snippet: str = Field(description="30-word window around the entity")
    source_offset: tuple[int, int]

class ExtractionResult(BaseModel):
    entities: List[EntitySpan]
    document_id: str
    model_version: str

class EntityExtractorAgent:
    def __init__(self, model: str = "gpt-4.1"):
        llm = ChatOpenAI(model=model, temperature=0)
        prompt = ChatPromptTemplate.from_messages([
            ("system", EXTRACTION_SYSTEM_PROMPT),
            ("human", "Document ID: {doc_id}\n\nText:\n{text}")
        ])
        self.chain = prompt | llm.with_structured_output(ExtractionResult)

    def extract(self, text: str, doc_id: str) -> ExtractionResult:
        return self.chain.invoke({"text": text, "doc_id": doc_id})

The key design decision here is the use of with_structured_output() to enforce Pydantic schema compliance. Raw LLM output is unreliable for downstream agents that expect typed data — structured output eliminates an entire class of parsing bugs. The source_offset field preserves provenance so that every mapping decision can be traced back to the exact position in the source document.

5. Agent 2 — OntologyMapperAgent

The mapping agent is the most computationally intensive component. For each extracted entity, it performs three parallel operations: (1) a full-text search of BioPortal's annotator API across a curated subset of 12 ontologies relevant to pharmaceutical R&D; (2) an OLS4 search via EBI's REST API; and (3) a semantic similarity ranking using sentence-transformer embeddings of ontology term definitions against the entity's context snippet.

ontology_mapper.py 
import asyncio
from dataclasses import dataclass
from typing import List
from sentence_transformers import SentenceTransformer, util

@dataclass
class MappingCandidate:
    curie: str                 # e.g. "OBI:0001985"
    label: str                 # e.g. "cell viability assay"
    ontology: str              # e.g. "OBI"
    ic_score: float            # information content (0–1)
    semantic_sim: float        # cosine similarity to entity context
    combined_score: float      # weighted: 0.6*ic + 0.4*semantic_sim
    definition: str
    source: str               # "bioportal" | "ols4"

class OntologyMapperAgent:
    PRIORITY_ONTOLOGIES = ["OBI", "BAO", "GO", "CHEBI", "NCIT", "HP",
                           "EFO", "CLO", "IAO", "SBO", "UO", "PATO"]

    def __init__(self):
        self.embedder = SentenceTransformer("pritamdeka/S-PubMedBert-MS-MARCO")

    async def map_entity(self, entity: EntitySpan) -> List[MappingCandidate]:
        # Fire BioPortal and OLS4 searches concurrently
        bp_results, ols_results = await asyncio.gather(
            self._search_bioportal(entity.normalized, entity.entity_type),
            self._search_ols4(entity.normalized, entity.entity_type),
        )
        candidates = bp_results + ols_results
        candidates = self._deduplicate_by_curie(candidates)
        candidates = self._rank_by_semantic_similarity(candidates, entity.context_snippet)
        return sorted(candidates, key=lambda c: c.combined_score, reverse=True)[:3]

The ranking function deserves explanation. Information Content (IC) is a standard ontology metric that measures how specific a term is — a term with many children (like "biological process") has low IC; a leaf-node term has high IC. For curation purposes, we want the most specific correct term, so IC is the primary signal. Semantic similarity against the entity's context snippet (the 30-word window captured by the extractor) handles cases where the IC ranking would surface the technically-correct-but-contextually-wrong term.

Model choice matters Generic sentence transformers (e.g., all-MiniLM-L6-v2) perform poorly on biomedical ontology matching because they lack domain vocabulary. S-PubMedBert-MS-MARCO, fine-tuned on PubMed text and the MS MARCO retrieval task, shows 18% higher precision@1 on the CRAFT corpus benchmark compared to the generic model.

6. Agent 3 — ConflictDetectorAgent

Conflict detection is the step that single-call architectures entirely miss. The ConflictDetectorAgent compares each new mapping proposal against the organization's existing ontology registry — a PostgreSQL-backed store of all previously approved term mappings, cross-referenced by dataset, system, and domain.

Two conflict types are detected:

  • Synonym conflict. Two different source strings (e.g., "VIAB %" and "Cell Viability") are proposed as mapping to two different CURIEs. One of them must be wrong, or a synonym relationship must be explicitly registered.
  • Homonym conflict. The same source string is used in two different systems but refers to semantically distinct concepts (e.g., "yield" means molar yield in chemistry and process step yield in manufacturing).
conflict_detector.py 
from enum import Enum
from dataclasses import dataclass, field
from typing import List, Optional

class ConflictType(Enum):
    SYNONYM  = "synonym_conflict"   # same concept, different CURIEs
    HOMONYM  = "homonym_conflict"   # same string, different concepts
    ORPHAN   = "orphan"             # no existing registry entry — new term
    APPROVED = "pre_approved"       # exact match to approved mapping

@dataclass
class ConflictReport:
    entity: EntitySpan
    proposed_mapping: MappingCandidate
    conflict_type: ConflictType
    existing_curie: Optional[str] = None
    existing_dataset: Optional[str] = None
    confidence: float = 1.0
    requires_human_review: bool = False
    suggested_resolution: str = ""

class ConflictDetectorAgent:
    def analyze(self, candidates: List[MappingCandidate],
                  entity: EntitySpan) -> ConflictReport:
        existing = self.registry.lookup(entity.normalized, entity.entity_type)
        best = candidates[0]

        if not existing:
            return ConflictReport(entity, best, ConflictType.ORPHAN,
                requires_human_review=best.combined_score < 0.85)

        if existing.curie == best.curie:
            return ConflictReport(entity, best, ConflictType.APPROVED)

        conflict = ConflictType.SYNONYM if \
            self._same_concept(existing.curie, best.curie) else ConflictType.HOMONYM
        return ConflictReport(entity, best, conflict,
            existing_curie=existing.curie,
            requires_human_review=True)

The _same_concept() method uses OWL reasoning via a locally cached ontology graph (loaded with owlready2) to check whether two CURIEs are equivalent classes, subclass-of, or semantically disjoint. This distinguishes a synonym conflict — where the resolution is to register an alias — from a homonym conflict, which requires domain expert judgment.

7. Agent 4 — GovernanceRouterAgent

The final agent implements the decision logic that determines the disposition of each mapping proposal. It applies a tiered routing policy:

  • Auto-approve — ConflictType.APPROVED (exact registry match) or ConflictType.ORPHAN with combined_score ≥ 0.92 and a Priority 1 ontology. These are written directly to the registry with a source=AUTO_APPROVED tag.
  • Steward review — All conflicts and orphans with 0.75 ≤ score < 0.92. Routed to the named domain steward for the entity's scientific domain. The steward receives a structured review card with the proposed mapping, the top-3 alternatives, and the evidence chain.
  • Board escalation — Novel entity types not covered by existing ontologies, or homonym conflicts involving core platform terminologies. These go to the ontology governance board for a formal vote.
governance_router.py 
from enum import Enum

class Disposition(Enum):
    AUTO_APPROVED   = "auto_approved"
    STEWARD_REVIEW  = "steward_review"
    BOARD_ESCALATED = "board_escalated"
    REJECTED        = "rejected"

class GovernanceRouterAgent:
    def route(self, report: ConflictReport) -> GovernanceDecision:
        # Tier 1: auto-approve
        if report.conflict_type == ConflictType.APPROVED:
            return GovernanceDecision(Disposition.AUTO_APPROVED, report)

        if (report.conflict_type == ConflictType.ORPHAN
                and not report.requires_human_review
                and report.proposed_mapping.ontology in self.PRIORITY_ONTOLOGIES):
            return GovernanceDecision(Disposition.AUTO_APPROVED, report)

        # Tier 2: steward review for all conflicts and low-confidence orphans
        steward = self.steward_registry.get(report.entity.entity_type,
                                             domain=report.proposed_mapping.ontology)
        if steward and report.conflict_type != ConflictType.HOMONYM:
            return GovernanceDecision(Disposition.STEWARD_REVIEW, report,
                                        assigned_to=steward.email,
                                        due_date=self._sla_date(hours=72))

        # Tier 3: board escalation
        return GovernanceDecision(Disposition.BOARD_ESCALATED, report)

8. The LangGraph State Machine

LangGraph provides the orchestration layer that connects the four agents into a coherent pipeline. The core design is a typed state object (CurationState) that flows through the graph, accumulating results at each node. Conditional edges implement the routing logic.

pipeline.py 
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver
from typing import TypedDict, List, Optional

class CurationState(TypedDict):
    document_id: str
    raw_text: str
    entities: List[EntitySpan]
    candidates: List[MappingCandidate]
    conflicts: List[ConflictReport]
    decisions: List[GovernanceDecision]
    requires_interrupt: bool
    steward_feedback: Optional[str]

def build_graph(checkpointer) -> StateGraph:
    graph = StateGraph(CurationState)

    graph.add_node("extract",   extractor_node)
    graph.add_node("map",       mapper_node)
    graph.add_node("detect",    conflict_node)
    graph.add_node("govern",    governance_node)
    graph.add_node("interrupt", human_review_node)   # HITL gate
    graph.add_node("commit",    registry_write_node)

    graph.set_entry_point("extract")
    graph.add_edge("extract", "map")
    graph.add_edge("map",     "detect")
    graph.add_edge("detect",  "govern")

    # Conditional: interrupt for human review or commit directly
    graph.add_conditional_edges("govern", route_after_governance,
        {"human_review": "interrupt", "auto": "commit"})
    graph.add_edge("interrupt", "commit")
    graph.add_edge("commit",   END)

    return graph.compile(checkpointer=checkpointer,
                          interrupt_before=["interrupt"])

The interrupt_before=["interrupt"] parameter is the key to human-in-the-loop integration. When the graph reaches the interrupt node, execution suspends and persists its state to the PostgreSQL checkpointer. The steward receives a notification, reviews the proposal in the governance UI, and resumes the graph with their decision. The full audit trail — every state transition, every agent's reasoning, the steward's rationale — is stored in the checkpoint database.

9. Human-in-the-Loop Governance

The governance layer is not an afterthought — it is the primary differentiator of this architecture from a fully-automated pipeline. Pharmaceutical R&D operates under regulatory oversight; terminology decisions that affect clinical data or regulatory submissions require documented human approval. The system is designed so that a steward's decision is never implicit — it is always an explicit, time-stamped action tied to a named individual.

The governance UI presents each review item as a structured decision card containing:

  • The source document context (the 30-word snippet with the entity highlighted)
  • The proposed mapping with its confidence breakdown (IC score + semantic similarity)
  • The top-3 alternatives ranked by combined score
  • The conflict description with the conflicting existing mapping
  • A free-text rationale field (required for board-escalated items)
  • Approve / Reject / Request-Synonym / Escalate action buttons
Governance as a first-class product feature Early prototypes treated human review as a fallback for low-confidence cases. User research with domain stewards revealed that they wanted to see the agent's reasoning for all decisions, not just the uncertain ones — because the auto-approved cases were the ones most likely to propagate errors silently. The production system now sends a weekly digest of all auto-approved mappings to relevant stewards, with a 7-day window to flag exceptions.

10. Results and Impact

The system was piloted on three years of historical assay data across two therapeutic areas. The comparison baseline was the previous manual curation workflow: a Jira-based process where scientists submitted terminology proposals and stewards reviewed them asynchronously, with an average resolution time of 18 days.

The 83% auto-approval rate means that domain stewards now only actively review one in six incoming terminology proposals. Of the reviewed cases, 96% result in the steward selecting the agent's top-ranked candidate — confirming that the mapping quality is high enough to warrant the confidence threshold.

The most significant impact is the elimination of the backlog effect. Under the manual workflow, curation bottlenecks caused new dataset ingestions to be delayed by 2–6 weeks while terminologies were resolved. The agentic pipeline removes this bottleneck entirely for the 83% of auto-approved cases; even the human-reviewed cases resolve within hours rather than weeks because the steward receives a pre-analyzed decision card rather than a raw proposal.

11. Lessons Learned

Start with the governance workflow, not the AI

The most important early decision was to design the human review workflow before writing any AI code. Understanding exactly what a steward needs to see in order to make a confident decision shaped every data structure in the system — the context snippet, the confidence breakdown, the conflict report format. Systems that add governance as an afterthought end up with UIs that provide insufficient context for good decisions.

Structured output is not optional

Using with_structured_output() throughout the pipeline eliminated an entire class of integration bugs. Agents that return free text require fragile parsing logic in every downstream component. With Pydantic schemas enforced at the LLM output boundary, the graph state is always well-typed and the failure mode for a bad LLM response is a clean validation error rather than a silent data corruption.

The BioPortal rate limit is your bottleneck

BioPortal's free API tier allows 15 requests per second. For bulk curation of historical datasets, this becomes the dominant constraint. The production system uses an aggressive local caching layer (Redis, TTL 30 days for stable ontologies) that satisfies ~70% of lookups from cache, reducing API calls to a manageable rate. For high-volume deployments, the NCBO team offers an on-premise BioPortal instance.

Conflict detection is where the value is

The extraction and mapping steps are well-served by existing tools. The genuine novel contribution of this architecture is the cross-dataset conflict detector. In evaluations, this component surfaced 14 terminology conflicts in the historical data that had existed for 2–3 years without being detected — inconsistencies that were silently corrupting cross-study analytics.

LangGraph checkpointing enables forensic debugging

The PostgreSQL checkpointer stores the full graph state at every node, for every run. When a steward disagrees with an auto-approved mapping, the complete reasoning chain — which documents were ingested, what context was captured, what BioPortal candidates were returned and their scores — is available for retrospective review. This forensic capability was essential for building steward trust in the system.

What's next The next version of OntoCurator will add a ProvenanceTraceAgent that generates PROV-O compatible lineage graphs for each mapping decision — enabling downstream FAIR assessors to score metadata interoperability (RDA indicator RDA-I3-01M) automatically by reading the provenance graph rather than relying on manual evidence documentation.
